DATABASE SCHEMA NOTES — PAYMENT DOMAIN
The fictional payments database contains the following logical entities.

merchant(merchant_id, legal_name, status, created_at)
payment(payment_id, merchant_id, merchant_reference, amount_minor, currency, status, created_at)
payment_event(event_id, payment_id, event_type, event_timestamp, source)
ledger_entry(entry_id, payment_id, account_id, debit_credit, amount_minor, currency, posted_at)
settlement_batch(batch_id, merchant_id, settlement_date, status, total_amount_minor)

Relationships
A merchant can have many payments. A payment can have many payment events and ledger entries. A merchant can have many settlement batches.

Design notes
Use immutable event records for lifecycle history. Apply appropriate indexes to merchant_id, merchant_reference, status, and created_at based on query patterns. Do not assume that a payment row alone is a complete audit trail.
